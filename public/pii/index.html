Summary of exposure

Without filterWith filter

Also in the pull request experimental · not deployed yet

  • Tasks. In redact mode, string values in a task's JSON input are redacted and the task runs. Block mode answers 422, naming the types. Schema errors never quote a value. 
    {"name": "ClientError", "message": "Input blocked by guardrails",
 "details": {"category": "pii", "entities": ["PHONE"]}}
  • Block names the type. The refusal is a stream event with category pii. Its message and entities name the types, never the values. 
    {"type": "data-guardrail-violation",
 "data": {"category": "pii", "guardrailType": "input",
  "fallbackResponse": "Your message seems to contain sensitive personal data (payment card number), so it was not processed. Remove it and try again.",
  "entities": ["CREDIT_CARD"]}}
  • Detection. It uses kit v0.2.1, and also catches grouped or lowercase IBANs, a card followed by its expiry, and cards split by dots, tabs, line breaks or spaced hyphens. A phone with no + and no spaces needs a word like “call” first.
  • Only new input blocks: user messages after the last agent reply. Earlier turns and replies sent back are redacted silently. So is a stored message resent unchanged.
  • Limits. A request with over 32,000 new characters is refused. Tool data and the system prompt are not checked. ≈1.6% of EAN-13 barcodes and ≈2.6% of 16-digit order numbers read as cards. An identifier split across two JSON values of a task input is missed.

This page runs none of this; its own filter here misses most of the detection above.
