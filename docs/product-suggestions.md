# Product suggestions for Agent Studio

Things this demo wanted, could not have, and worked around. Each one is written
from a workaround that exists in this repo, so the cost of not having it is
concrete rather than hypothetical.

Ordered by how much the workaround costs.

---

## 1. `instructions` on `/context/compact`

**What we wanted.** To steer a summary — "outline the chapter titles, at most 250
words, no preamble" — without that instruction being part of what gets
summarized.

**What exists.** `/1/unstable/context/compact` summarizes the messages you give
it. There is no separate channel for how to summarize them. So steering has to be
smuggled in as content.

**The workaround, and why it fails.** `scripts/../public/chat-with-book/app.js`
wraps each section like this:

```
Section 3 of 16 of a long document. Write a compact outline of at most 250
words: … no preamble, no closing remarks.

<60,000 tokens of War and Peace>

End of section 3 of 16. Now write that outline: at most 250 words, titles in
order, one clause each.
```

The cap is stated twice, before and after, because stated only once at the top —
60k tokens away from where the answer begins — sections that are mostly verse
came back quoted rather than outlined, at 3,050 tokens against a 250-word
instruction, which then made the reduce four times slower. That duplication is
already a bad smell. It also does not hold: on the reference book the summarizer
starts summarizing the instructions.

Observed output, map pass:

> You have provided the first section of War and Peace. I will outline these
> chapters as follows: …

Observed output, reduce pass — a 403-token "joint digest" that contains no digest:

> You have been providing 16 sections of a long document … You have specified a
> strict format for the output: Keep the order and the chapter/section titles.
> List each title followed by exactly one short clause … You are waiting for the
> final merged document that follows all these constraints.

The model is not misbehaving. It was handed a document that consists mostly of
instructions and asked to summarize the document.

**Proposal.** `instructions: str | None` on the compact request, applied as the
summarizer's own prompt and never treated as content. A `maxWords` or `maxTokens`
cap alongside it would remove the second half of the workaround.

**Why it generalizes.** Any caller doing map-reduce over long documents hits
this, and every one of them will invent the same fragile framing. Compaction with
a caller-supplied objective is the difference between "make this smaller" and
"make this smaller, keeping what I care about".

## 2. Suggestions without an answer

**What we wanted.** Three opening questions for a book the reader just put into
the conversation, before they have asked anything.

**What exists.** `suggestions: {enabled: true, …}` in agent config, generated by a
node that runs **as part of a completion** and streamed as a `data-suggestions`
frame. Excellent once a conversation exists. There is no path to it with zero
user input: no standalone endpoint, and no way to ask for suggestions without
also generating an answer.

**The workaround.** The book page ships two hand-written openings per book — 32
curated strings in `public/shared/books.js` — and the follow-up row carries an
italic "after your first question" until the first answer lands. It is honest,
and it is 32 strings that a model could have written from the text, plus a rail
that is visibly empty on the screen a first-time visitor sees.

The alternative we did not take: spend one hidden completion on book load and
discard the answer. Rejected because this demo's whole argument is an honest token
meter, and a hidden call is either invisible (the meter lies) or visible (the
reader wonders why the assistant said hello).

**Proposal, cheapest first.**

1. `?suggestionsOnly=true` on `/1/agents/{id}/completions` — run the suggestions
   node, skip the answer node, stream `data-suggestions` then `[DONE]`. No new
   endpoint, no new config, and it composes with everything that already works.
2. Or `POST /1/agents/{id}/suggestions` taking messages and returning a list.
3. Either way, allow generation from context alone. A conversation whose only
   message is a pasted document is a perfectly good basis for "what could I ask
   about this?" — arguably the best one.

**Why it generalizes.** Cold start is the moment a demo, a docs page, or a search
UI most needs suggestions, and it is the one moment the current design cannot
serve. Every integrator will hand-write an opening set, and every hand-written
set will drift from the corpus behind it.

## 3. Compact JSON separators for tool results

**What we wanted.** Cheaper tool-result payloads without changing their shape.

**What exists.** `tool_results_format` (`json | toon | yaml | markdown_kv`, PR
#1362). Measured on this index with the real tokenizer, 360/360 points:

| format | vs JSON |
|---|---|
| `toon` | +16.0% to +17.2% on flat records, **0.00% on any nested payload** |
| `yaml` | −0.7% to −7.7% — *costs more*, everywhere |
| `markdown_kv` | +0.3% to +1.1% — noise |
| compact JSON separators | **+2.3% to +8.6%, on every payload including nested** |

TOON's entire win is dropped per-record key names — a constant ~16 tokens per
record — so the saving is `16 / record_size` and record shape is a ~10× lever
where encoding is at best 1.21×. It also silently declines any array whose objects
hold nested values, so turning it on while `attributesToSnippet` is set yields
exactly 0.00% and no warning.

**Proposal.** `json.dumps(…, separators=(",", ":"))` as the default JSON
serialization for tool results. No flag, no format negotiation, no behaviour
change — the same bytes minus the spaces. It is the only option measured here that
helps the nested payloads real search configurations actually return.

## 4. Smaller things found on the way

- **`enableAlgoliaMcp` reads as a switch and is not one.** The completions router
  ORs the agent-config field with a query param *and* the `algolia_mcp_enabled`
  feature flag, so an operator setting `false` gets MCP anyway, silently. Either
  let agent config opt out, or reject/warn on a value that cannot take effect.
- **`attributesForFaceting` can break tool calling outright.** The MCP server
  generates one `facet_<attribute>` parameter per faceted attribute. With
  `["book","author","chapter"]` declared, the model sent
  `facet_book: "Moby-Dick; or, The Whale"` and got `'Moby-Dick; or, The Whale' is
  not valid under any of the given schemas` — seven times in one turn, after which
  the agent apologised for not finding a passage that was sitting in the index. A
  facet value the index genuinely contains should not be unrepresentable. The
  undocumented `?nullableFacetParameters=true` suggests this area is known-rough.
- **`distinct` reaches the MCP server through the legacy door only.**
  `searchControls.distinct` is stripped unless `algolia_mcp_distinct_enabled` is
  on, while `searchParameters` is forwarded into `custom` without that strip — so
  the deprecated-looking field is the one that works. Worth making consistent.
- **A rejected tool call emits `tool-input-error` *instead of*
  `tool-input-available`.** Reasonable, but undocumented, and any UI keyed on
  `-available` renders nothing at all for failures. Ours did, which is how the
  facet bug above shipped unnoticed.
- **The tool name in config is not the tool name the model sees** — it becomes
  `algolia_search_index_<index>`. Instructions that name your configured tool
  refer to something that does not exist.
